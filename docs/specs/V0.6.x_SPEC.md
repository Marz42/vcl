# Vincula 0.6.x 开发规格与可行性研究

> 状态：开工规格草案，2026-11-19。可行性研究、子版本 G0 和实机验收均待执行。
> 基线：0.5.5 已通过 H05，并经 [PR #15](https://github.com/Marz42/vcl/pull/15) 合入 `main`（`9cab4ac`）。运行时与现场证据绑定原 RC，开发从合入后的 `main` 核对实际基线。

本规格定义 0.6.0～0.6.4 的交付行为和研究判据。[Master SPEC](VCL_0.5-0.7_Master_SPEC.md) 定义跨版本不变量，[实施方案](../plans/VCL_0.5-0.7_Implementation_Plan.md) 维护实施步骤与 AC，[人工验收清单](../plans/VCL_0.5-0.7_Human_Acceptance.md#h06-06x-declarative-controller) 记录 H06 放行要求。

## 1. 目标与范围

Controller 从期望状态和新鲜的观测事实生成变更计划，经人工批准后执行、验证并提交，失败时恢复上一份已验证可用配置（LKG）。首个端到端场景为在一台 VPS 上启用缺失的测试用户，经批准生效，重复协调返回 `NOOP`。首个网络实验使用同一入口上的两个测试用户，Alice 经授权 SOCKS5 出口，Bob 显式直出。由独立测试目标记录实际出口，验证 Alice 的 SOCKS5 故障与 Bob 隔离。

| 版本 | 交付 | 前置条件 |
| --- | --- | --- |
| 0.6.0 M0 | SSH 凭据闭环、受限 observer、结构化失败、有界批采样 | H05 PASS，0.5.5 基线 |
| 0.6.0 | Desired / Diff / Operation / LKG，受管端口、SNI 和 advertised server 变更（R-03） | M0 的身份与传输合同，受限写通道 |
| 0.6.1 | 告警、确认、静默、维护窗口、恢复通知 | 0.5.5 Finding / Timeline。告警状态可先做，维护审计接入 Operation 后集成 |
| 0.6.2 | Traffic Policy v0.1。逐用户 QoS 由独立研究关卡决定 | Desired/LKG 与共同路由编译合同 |
| 0.6.3 | 每用户 direct / SOCKS5 出口，TCP/HTTPS、DNS 与隔离实测 | Desired/LKG、凭据引用、Policy 优先级 |
| 0.6.4 | 受控维护、滚动升级、归档与有界修剪、R-14、Fleet Doctor | Operation、维护窗口、schema-5 与现有备份恢复合同 |

0.5.5 是最低受支持的现有 Node 基线，支持其已声明的观测与升级能力。0.6 写入要求目标 Node 宣告对应用例的 capability。更早 Node 作为历史资料或单独恢复流程的输入。Controller 与 Node 混合版本由能力协商处理，缺能力显示 `UNSUPPORTED`。版本集成按依赖推进，0.6.3 的隔离实验可在首个完整 LKG 事务后开展，0.6.2 Tier 2 研究可独立进行。

Controller 持有唯一 Desired 权威。Controller 或 observation/accountd 离线时，Node 继续运行最近已提交的数据面状态。出口故障按已选择的策略拒绝请求。数据面变更通过受限的 typed dispatcher 执行。0.6.x 的发布范围是单 Node 上的路由、策略和维护能力，跨 Node Path、无人值守选路和自动失败回切属于后续阶段。

### 2.2 实验与选型

每项研究先登记假设、候选版本与 digest、实验角色、环境、采样方法、通过判据、上限和复原步骤。用隔离 Workspace、短期测试身份、可恢复的测试机器和自控或获准目标。脚本夹具与本地模拟先验证故障分支，实机矩阵记录实际结果。每项结论附脱敏测量和决策记录（ADR），给出 `PASS`、`BLOCKED` 或获准的 `DEFERRED`。需要实机且环境未就绪的项目记 `PENDING LIVE`。

## 3. 0.6.0 M0 与声明式事务

### 3.1 凭据与只读采样

- 生命周期入口共享既有凭据引用和 Agent 指纹选择能力，校验 observer 的公钥类型与目标主机身份。只有明确的受管安装、同步密钥或轮换操作可写 observer 配置。新 observer 凭据须通过独立 `identity` 验证后才报告就绪。退出、失败或恢复途中按真实状态报告。
- 管理与观察分别绑定 SSH 用户、主机身份和凭据。`observe` 缺配置或校验失败直接返回结构化结果，禁用隐式 admin/root 回退。持久诊断保留固定 `phase`、`code`、`TIMEOUT`，错误输出按脱敏合同收敛。
- 批响应以版本化能力协商，分项限制时间、大小和条目数。支持批协议时每轮最多一条 observer SSH 请求，`inspect` 保留独立、可配置的较低频率。未宣告能力的 0.5.5 保留受限逐项只读采样。连接复用按 host/port、known_hosts、用户、凭据类与凭据指纹隔离，密钥撤销或绑定变更使旧连接失效。Windows 基线可用无复用模式。

### 3.2 Desired、计划与锁

| 内容 | 合同 |
| --- | --- |
| Desired | Workspace 管理稳定 Node/User/Deployment ID、配置 revision 和期望绑定。已有节点通过显式导入/复核纳管。`Policy` 和 `Egress` 以稳定引用扩展。现有审计数据及客户端身份保持可用。 |
| Observed / Diff | 按 `node_id`、`instance_id`、capability、观测时间和投影版本确认事实。输出 `MATCH` / `DRIFT` / `MISSING` / `EXTRA` / `DEGRADED` / `UNKNOWN`。变更计划只覆盖有充足观测的受管差异，删除已有资源须在计划中明确列出。 |
| Operation | 固化计划 ID、动作类型、目标、Workspace revision、Node 配置代次与指纹、能力、凭据版本引用、风险、影响范围、后置条件与回滚条件。批准绑定计划内容与有效期。计划与日志只含非密钥字段。 |
| Apply | Controller 二次检查审批与 Workspace revision。Node 持有变更锁后检查目标实例、配置代次和前置条件，再接受同一 operation ID。旧 CLI 及维护入口使用同一 Node 锁。前置条件不满足返回 `PLAN_STALE`。同一计划重试查询已记录的结果或续作；已达成返回 `NOOP`。 |

### 3.3 提交点、回滚与 R-03

1. 持久化操作记录、恢复入口和旧 LKG 引用。生成完整候选，校验 schema、权限、secret 引用、sing-box 配置和受管文件归属。
2. 将候选写入受限 staging。以可恢复的 generation 和提交标记激活，进程退出后可确定旧、新配置与有效运行状态。运行时健康和真实代理后置检查通过才更新 LKG 并标记成功。
3. 配置无效时拒绝激活。生效后验证失败则恢复旧配置并重验。回滚失败、状态无法确定或跨 Node 部分完成时报告 `PARTIAL`，保留恢复指引及证据。凭据撤销等安全边界适用于回滚。Controller 离线后已开始的事务按 Node 本地恢复合同有界结束。
4. R-03 验证监听端口/SNI/advertised server 变更、客户端元数据更新提示与回退，保留适用的用户 identity、Node/instance identity 和 accounting。计划内的连接中断与出站探针结果均记录。

对应实施项 AC-6.0-00～06。首个可验证交付围绕「显式批准启用缺失测试用户、重复 `NOOP`、中断恢复与 `PLAN_STALE`」，随后扩展 R-03。`lib/access.py`、`lib/ssh_transport.py`、`lib/observer.py`、`lib/workspace.py` 与既有升级恢复代码是优先复用点。

## 4. 0.6.1 告警与事件操作

- 原始事实、Finding 活跃/恢复、确认与静默、通知投递状态分别存储。按 Node / Finding 类型聚合，处理 `SYNC_LAG` 的预期陈旧与正常突发流量，保留恢复和同期无关故障。
- 通知使用有界队列、持久去重、有限重试与恢复通知。首个适配器为 Webhook，接收端由操作者明确选定，token 走 secret-ref。队列满、远端限流和发送失败体现在投递健康，采样和转发照常运行。
- 维护窗口有目标、原因和截止时间，作用域限定为计划内影响。确认、静默、到期和窗口变更进入 journal。AC-6.1-01～05 覆盖单一故障聚合、恢复、静默边界、渠道故障、重启及连续 24h。

## 5. 0.6.2 Traffic Policy 与逐用户 QoS

### 5.1 Tier 1（H06 必需）

`RuleGroup` 保存稳定 ID、规则版本和匹配条件，用户绑定引用该资源。冻结编译优先级，先匹配显式拒绝，再进入用户绑定的出口；`allow` 表达策略放行并继续受该用户出口约束。无匹配时进入明确声明的默认动作。用同一编译器处理 Policy 与 Egress，并用脱敏观测验证运行中的规则版本。

域名规则限定于 Entry 实际可获得的匹配信息。预解析 IP、DoH、QUIC 等输入按能力矩阵验收。命中事件至少记录用户的稳定引用、规则组与版本、动作、时间及 Node，字段受脱敏和容量约束。Alice 被拒、Bob 放行，且 Alice 绑定 SOCKS5 后阻断仍优先，是必需实机用例（AC-6.2-00、AC-6.3-01）。

### 5.2 Tier 2（由 F06-05 决定）

通过研究后才冻结限速方向、单位、burst、连接软告警和可支持的硬限制。规则由 VCL 标注所有权，经同一审批、事务、restart/rollback 验证。限时策略到期行为随计划批准，测试 Controller 离线时的行为。Finding 可产出建议，经人工批准生效。

H06 候选冻结前记录 `PASS` 或 `DEFERRED`。`DEFERRED` 记录已尝试方案、未通过判据、关闭的 capability、用户可见限制及重开条件。H06 记录明确签署 Tier 1 和 Tier 2 的范围。Tier 2 一旦纳入候选，AC-6.2-01～06 的适用条目、实机与 soak 均按冻结范围通过。未交付的强制限制在 plan 阶段显式拒绝。

## 6. 0.6.3 逐用户出口与实机实验

- `Egress` 保存稳定 ID、类型（`direct` / `socks5`）、受管地址、协议能力、DNS 策略与 credential ref。User 仅引用 Egress。实现先覆盖受限、可信链路上的 no-auth 与用户名密码认证。密码在未加密链路上以明文传输，认证实验使用可信私网或加密传输。只有 Node 服务所需的受限配置可持有解析后的凭据。 [SOCKS5 用户名密码认证](https://www.rfc-editor.org/info/rfc1929/)
- DNS 合同分别描述客户端解析、Node 引导解析与目标解析。验证目标域名按预期由指定一端解析，解析失败遵循已选择的出口策略。首版必须通过 TCP/HTTPS、约定的 DNS 行为、实际出口与隔离。UDP/QUIC/HTTP3 写明逐项实测结果、支持条件与显式失败方式。不支持的协议/地址族按已批准策略拒绝。
- 运行时探针按 TCP 可达、认证、CONNECT、实际出口地址与 HTTPS 请求分段报告，且受目标、频率和超时限制。Endpoint 故障使绑定用户失败，保留其他用户可用性。覆盖错误密码、黑洞超时、解析器故障、路由去活、secret 轮换与回滚。
- F06-06 与 AC-6.3-01～06 分别验证研究结论和候选制品。抓取的信息限制在授权目标与脱敏结果。用业务探针与连接证据判定成功，CLI/UI 从共享服务读取有效状态。

## 8. 实施与验收入口

1. 从合入后的 `main` 核对 Controller/Node 包、schema 5、H05 签署与本地未提交文档，登记基线 SHA。先做 F06-01、F06-02 的离线基线和隔离实机矩阵，同时准备两个测试身份与可控目标。
2. 每个子版本在 G0 冻结 schema、capability、CLI/JSON 合同、前后兼容、执行预算和 Live 矩阵。对应 AC 必须有故障注入与实际后置条件。G1～G5 依次验证离线、集成、安全、现场与固定候选 soak。
3. 固定 0.6.4 RC 以同一候选完成 ≥24h 综合 soak。H06 人工见证声明式变更与回滚、两用户策略/出口隔离、告警恢复、维护能力和签署范围。QoS 有实测通过或明确延期记录。证据绑定候选 SHA、digest、配置 revision、窗口与脱敏拓扑。
4. H06 后正式集成 0.7.x。路径切换需人工批准固定目标，可立即执行或在限定窗口内等待指定用户空闲后执行。到期撤销等待，观测未知时继续等待。目标用户旧会话可能中断，逐用户切换应保持无关用户可用。详细验收归 [0.7.3 实施方案](../plans/VCL_0.5-0.7_Implementation_Plan.md#path-switch-073)。
