## 一、版本定位

0.4.5 的定位为：

> VCL 0.4 系列的 Integration & Hardening 版本，同时新增一个严格受限的 Legacy single-user seed 功能。

不要加入以下 0.5.x 功能：

- Telemetry/monitoring protocol；
- observe credential routing；
- SNI 自动调优；
- UI 管理类高危操作；
- 通用 VLESS/Xray/sing-box 配置导入；
- 多用户 legacy migration；
- 新的远程管理端口或 API。

## 二、版本契约

Legacy seed 会修改节点安装制品，因此不得修改代码后继续将节点包标记为不可变的 Node 0.3.1。

目标版本：

- Controller：0.4.5
- 新 provision payload：Node 0.3.2
- Controller 0.4.5 最低兼容 Node：0.3.1
- Legacy seed capability：要求 Node 0.3.2
- 已有 Node 0.3.1 不强制升级

更新以下内容：

- controller/node 版本常量；
- controller payload pin；
- artifact 文件名和 digest；
- payload manifest；
- Compatibility Matrix；
- Node Upgrade Contract；
- 路线图中“首次 Node 升级为 0.5.0”的旧表述；
- CHANGELOG、manual 和 release evidence。

如实现 Node 0.3.1 → 0.3.2 原地升级，必须保留：

- node_id；
- instance_id；
- Reality keypair；
- 所有用户 UUID；
- user_id/credential_id；
- accounting history；
- 已有 URI。

## 三、Legacy single-user seed

### 3.1 Controller CLI

在现有 provision 流程上增加：

```bash
vcl-fleet node provision NAME \
  --host VPS \
  --server ADVERTISED_HOST \
  --legacy-vless-uri-file ./legacy-user.uri \
  --legacy-reality-private-key-file ./reality-private.key \
  --legacy-user-tag existing-user

```

三项 legacy 参数必须同时出现。缺少任意一项时拒绝执行。

禁止把 URI、UUID、Reality 私钥直接放进：

- 命令行参数值；
- 环境变量；
- Workspace；
- registry；
- fleet cache；
- operations history；
- 普通日志。

argv 中只能出现本地文件路径。

### 3.2 Installer 支持

为 `vincula.sh` 增加对应的 file-based seed mode。Controller 应：

1. 检查本地 secret 文件；
2. 经已有可信 SSH 通道上传；
3. 使用权限为 `0700` 的随机 staging 目录；
4. secret 文件权限设为 `0600`；
5. 远端命令只传文件路径；
6. 成功或失败后均清理 staging；
7. 不在 installer 输出中回显 legacy URI、UUID 或私钥。

### 3.3 输入文件安全

本地输入必须：

- 是普通文件；
- 由当前用户拥有；
- 不允许 group/world readable；
- 不接受目录、FIFO、socket 等特殊文件；
- 对符号链接采用 fail-close 策略；
- URI 文件只接受**恰好一行**非空 URI（多行 / 多 URI = 多用户输入，拒绝）；
- 私钥文件只接受一个合法 Reality private key。

错误信息只能报告文件路径和错误类型，不得包含文件内容。

### 3.4 支持范围

只支持 VCL 固定协议：

- scheme：`vless`
- `encryption=none`
- `flow=xtls-rprx-vision`
- `security=reality`
- `type=tcp`
- 必须具有合法 UUID、SNI、public key 和端口
- Reality short ID 可缺省或为空（空 short ID，对应 URI 无 `sid` / `sid=`）
- Reality fingerprint 按 VCL 当前兼容值处理

明确拒绝：

- TLS、XTLS 非 Reality；
- WS、gRPC、HTTP、QUIC 等 transport；
- 缺少 pbk/sni；
- 非法 UUID；
- 非法 short ID（非空且非 0–16 hex）；
- 不兼容 flow；
- 多用户输入（URI 文件多于一行非空内容）；
- 任意 sing-box/Xray JSON 导入。

SSH `--host` 可以是管理地址，但旧 URI 的 authority 必须与 `--server` 一致；URI 端口即为安装监听端口（legacy seed 时 controller 从 URI 带入 `VCL_PORT`，**preflight 检查同一端口**）。否则拒绝，避免生成一个表面成功但旧客户端无法连接的节点。

### 3.5 Reality key 验证

安装写入前必须：

1. 从用户提供的 Reality private key 推导 public key；
2. 与 URI 中的 `pbk` 做常量时间或等价的严格比较；
3. 验证 short ID、SNI、UUID 和端口；
4. 使用原 UUID、private/public key、short ID 和 SNI 执行 Reality self-test；
5. self-test 通过后才能进入安装 mutation 阶段。

private key 与 pbk 不匹配必须 zero-install。

### 3.6 新节点身份

Seed 后生成一个全新的 VCL 节点，不迁移旧服务器状态。

必须新建：

- node_id；
- instance_id；
- Clash API secret；
- accounting database；
- install identity；
- VCL owner 的 user_id、credential_id 和 UUID；
- legacy 用户的 user_id、credential_id。

必须保留：

- legacy 用户原 UUID；
- Reality private/public key；
- Reality short ID；
- SNI；
- advertised server；
- VLESS port。

最终节点至少包含两个用户：

1. `owner`：VCL 新生成的管理员用户；
2. `--legacy-user-tag` 指定的普通用户：使用原 UUID。

`--legacy-user-tag owner` 必须拒绝。

原客户端中的 URI 不需要重新导入即可继续连接。URI fragment/显示名称不参与连接验收。

### 3.7 事务与回滚

沿用并强化当前 installer transaction contract：

- 预检和密钥验证必须发生在 mutation 之前；
- staged config 必须通过 `sing-box check`；
- sing-box 和 accountd 必须启动并通过健康检查；
- 完成前不得设置 `INSTALL_COMMITTED=1`；
- 失败时恢复为无 VCL 安装的 clean host；
- registry 只能在远端安装和 verify 成功后写入；
- registry 写入失败保持现有可恢复语义；
- initial `sync --full` 必须成功，否则按现有 PARTIAL 合约处理；
- 不允许出现安装失败但残留 VERSION 的状态。

### 3.8 成功输出

成功输出只能包含：

- 节点名称；
- Node 版本；
- legacy 用户 tag；
- provision/register/sync 状态；
- 获取链接的后续命令。

例如：

```text
Provisioned NAME (Node 0.3.2).
Legacy user existing-user seeded successfully.
Use `vcl-fleet user link existing-user --node NAME` to retrieve the URI.

```

不得自动打印 URI；不得打印 `node_id` / UUID / Reality 密钥。

## 四、0.4.4 UI 遗留收口

关闭 `docs/evidence/0.4.4/SUMMARY.md` 中的 PARTIAL 项。

### 4.1 Node Detail

API 已返回 `instances` 和 `recent_usage`，前端补充渲染：

- Instance History；
- started_at/ended_at/status；
- current/replaced instance；
- 近七日 usage；
- 空数据、异常数据和长字段显示。

不得增加 SSH GET 或 secret 展示。

### 4.2 User Detail

增加按用户聚合的 top destinations：

- 默认近七日；
- host、bytes、connections（无 network 列；不扩展 `daily_usage` schema）；
- 完全来自本地 cache；
- 没有数据时显示明确空状态；
- 不展示 credential UUID。

### 4.3 Operations history

将当前 UI-only `operations.jsonl` 改为 controller 公共 operation journal，使以下 CLI 操作也能进入 UI：

- provision；
- legacy seed provision；
- adopt；
- replace；
- user add；
- user rotate；
- backup（`node replace` 子步骤：remote `vcl backup create` / `--from-backup` 校验）；
- restore（`node replace` 子步骤：remote `vcl restore`；audit archive restore 记为 `audit_archive_restore`）；
- reseed；
- sync/probe/verify。

记录字段至少包括：

- operation_id；
- operation type；
- target；
- started_at/finished_at；
- state；
- exit code；
- controller version；
- 非敏感摘要。

禁止记录：

- 完整 argv；
- URI；
- UUID；
- Reality key；
- Clash secret；
- SSH private-key 内容；
- backup 路径中的 secret；
- backup age identity。

Operation journal 必须有损坏行容错和有界保留策略（文件锁 + 截断时原子 `os.replace`）。UI 仍然只能直接执行 D53 允许的操作；不得借此开放 provision/adopt/replace 等 UI mutation。
