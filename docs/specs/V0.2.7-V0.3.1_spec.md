# 1. 产品原则

## 1.1 内部工具优先

Vincula 假定：

- 管理员人数很少；
- 管理员控制 VPS 基础设施；
- 管理员工作站受信任；
- SSH 访问已经存在；
- 用户规模为数十到低数百，而非互联网级多租户；
- 可审计性与运维简洁优先于功能广度。

## 1.2 非计费级计量

Accounting 用于：

- 粗粒度用量可见性；
- 异常调查；
- 用户级审计；
- 目的地级审计；
- 容量与运维回顾。

Accounting **不是** 用于：

- 计费；
- 合同级流量计量；
- 字节级精确收费；
- 配额强制；
- 财务结算。

近似计量可接受。

但 accounting **必须** 满足：

> 误差可以存在，但必须有界，且不得通过重复记账、计数器复位、重启缺陷或错误 baseline 而累积。

## 1.3 审计窗口

默认 raw 审计保留：

```text
90 days
```

【覆盖原 SPEC §4.7】默认 daily 聚合保留 **同样冻结为 90 天**（决策 2 / D2），不再把 730 天当作默认策略。若未来需要 raw 90 / daily 730，必须独立实现 incremental immutable daily rollup；**现在不做**。

这是回答如下问题的主审查窗口：

```text
用户 Alice 在 2026-08-10 09:00 UTC 到 2026-08-10 18:00 UTC
访问了哪些目的地？
```

系统必须仅用元数据即可回答。

Vincula **不得** 要求 HTTPS MITM。

审计模型可以保留：

```text
user_id
node_id
instance_id
credential_id（在有用时）

started_at
last_seen_at
closed_at

destination_host
destination_ip
destination_port

upload_bytes
download_bytes
network/protocol metadata
```

Vincula **不得** 要求：

```text
URL path
HTTP body
TLS plaintext
页面内容
用户传输的凭据
```

## 1.4 低攻击面

服务端节点 **不得** 向公网暴露 Vincula 管理 API。

首选远程管理传输：

```text
SSH
SCP/SFTP（需要时）
```

允许的公网监听仍限于节点有意需要的服务，例如：

```text
SSH
代理协议监听器
```

任何未来 UI **必须** 仅存在于管理员工作站或 localhost-only。v0.3.1 第一版为只读，不做 Web 管理面板（决策 13 / D19）。

## 1.5 身份比基础设施更长寿

VPS 实例可替换。

长寿身份：

```text
user_id
logical node_id
audit history
accounting history
fleet configuration
```

较短寿资源包括：

```text
公网 IP
hostname
物理 VPS
instance_id
Reality keypair
credential UUID
Clash API secret
```

替换后的 VPS 可以拿到新凭据和新 IP，而不破坏逻辑用户身份或历史审计连续性。

# 2. 架构不变量

## INV-01 — 身份不是凭据

```text
user_id != VLESS/credential UUID
user_id != credential_id
```

`user_id` 是稳定的用户身份。

【决策 5】实现中 **全部身份字段采用 UUID 格式**（`user_id`、`node_id`、`instance_id`、`credential_id` 等）。`user_id` 本身是 UUID 字符串，但 **不是** 客户端凭据 UUID。旋转凭据不得创建新的逻辑用户。

本 SPEC 中的 `U-123`、`C-A`、`N-123`、`I-A` 等 **仅为示意标签**，不得实现为该字面格式。

## INV-02 — 逻辑节点不是物理实例

```text
node_id != instance_id
```

`node_id` 表示逻辑服务节点/线路。

`instance_id` 表示该逻辑节点的一次物理部署。

示例（示意标签；实现均为 UUID）：

```text
逻辑节点：
node_id = <现有 UUID，例如 6fc96a10-...>
name    = lax

旧 VPS：
instance_id = <UUID-A>
IP = 203.0.113.10

替换 VPS：
instance_id = <UUID-B>
IP = 203.0.113.28
```

两者属于同一个逻辑 `node_id`。

【覆盖原 SPEC】【决策 4 / D4】当前树上已经存在的 UUID `node_id`（写入 `state.json` / `config.toml` / `users.json` / accounting）**正式升格为逻辑节点 ID**。禁止重铸、改名或把 `node_id` 复制成 `instance_id`。改名将迫使历史回填，不采纳。

【D5】`instance_id` 在 v0.2.7 只预留可空列；在 v0.2.8 才为当前物理安装 mint 新的 `instance_id=UUID()`。

## INV-03 — 每节点凭据

一个用户可以存在于多个节点。

正确模型：

```text
相同 user_id
不同 credential_id
每节点不同 UUID
```

错误模型：

```text
同一 UUID 复制到所有节点
```

## INV-04 — 规范状态 vs 生成物

规范状态应与生成物明确分离。

推荐：

```text
Canonical:
  state.json
  users.json
  fleet registry
  accounting.db

Generated:
  sing-box/config.json
  VLESS URI
  CSV exports
  reports
  local UI views
```

生成物必须可从规范状态复现。

【决策 9 / D12】仓库布局：canonical = **仓库根目录**（`vincula.sh` / `bin/` / `lib/` / `scripts/`），generated = `dist/`。不搬迁到 `src/`。见 §15。

## INV-05 — 变更是事务性的（单节点）

改变认证、registry、节点状态或 restore 状态的 **单节点** 操作必须遵循：

```text
validate
→ stage
→ verify candidate
→ backup/transaction boundary
→ apply
→ health check
→ commit
```

失败必须导致：

```text
rollback
或
在变更前失败
```

单节点部分状态不可接受。

【覆盖原 SPEC INV-05 对分布式场景的「Partial state is not acceptable」】【决策 11 / D15】跨节点 Fleet 分布式变更 **不** 承诺分布式 rollback。状态机为：

```text
PLANNED → APPLYING → SUCCESS | PARTIAL
```

`PARTIAL` 必须列出每节点 `SUCCESS`/`FAILED` 以及补救命令。best-effort rollback 允许，但 **不是** correctness guarantee。

## INV-06 — 节点替换时不得静默复用密钥

替换 VPS 时，安全默认是：

```text
new Reality keypair
new Clash secret
new credential UUIDs
new instance_id
```

保留：

```text
user_id
node_id
audit history
accounting history
metadata
```

## 4.2 要求的 accounting 正确性模型

允许：

```text

```

禁止：

```text

负字节 delta
把 counter-reset 解释成巨额流量

connection ID 复用导致旧/新会话合并
崩溃/重启导致反复累积
已 closed 的 generation 被后来的 first sight 覆盖
JSONL 重启重放导致重复记账
```

## 4.3 持久化 baseline 与 schema 3（完整，非最小补丁）

【覆盖原 SPEC §4.3「exact schema MAY differ」中可逃避完整 schema 的空间。】【决策 16 / D6】v0.2.7 **必须** 实现完整 schema 3 + generation，不做「只在内存里修一下」的最小补丁。

当前（0.2.6 / 未发版树）为 `SCHEMA_VERSION = 2`：`connections.connection_id` 为 PRIMARY KEY，poll baseline 仅在进程内存 `_known_open` 中。这正是重启清零/覆盖的根因。

### 4.3.1 `connections`（至少）

```text
event_id          INTEGER PRIMARY KEY AUTOINCREMENT
connection_id     TEXT NOT NULL
generation        INTEGER NOT NULL
UNIQUE(connection_id, generation)

user_id           TEXT NOT NULL
node_id           TEXT NOT NULL
instance_id       TEXT NULL          -- 0.2.7 只预留；见 D5
user_tag          TEXT               -- 可保留，便于运维显示

started_at        TEXT NOT NULL      -- RFC3339 UTC
last_seen_at      TEXT NOT NULL
closed_at         TEXT               -- NULL = still open

destination_host  TEXT
destination_ip    TEXT
destination_port  INTEGER
network           TEXT

upload_bytes      INTEGER NOT NULL DEFAULT 0
download_bytes    INTEGER NOT NULL DEFAULT 0
```

`event_id`：SQLite `AUTOINCREMENT`（删除后 **不复用**）（D9）。  
`instance_id`：0.2.7 可空；`NULL` 的含义固定为 `'physical instance identity was not tracked at that time'`（D5）。**禁止** 把 `node_id` 的值复制进 `instance_id`。

### 4.3.2 `poll_baseline`（durable，DB 是唯一 commit point）

```text
connection_id           TEXT PRIMARY KEY
generation              INTEGER NOT NULL
last_upload_counter     INTEGER NOT NULL
last_download_counter   INTEGER NOT NULL
accounted_upload        INTEGER NOT NULL
accounted_download      INTEGER NOT NULL
last_seen_at            TEXT NOT NULL
```

### 4.3.3 核心不变量（D6）

> **已 closed 的 generation 永远不能被后来的 first sight 覆盖。**

若同一 `connection_id` 再次出现（sing-box 重启、ID 复用、accountd 重启后再次看见）：

- 若 DB 中该 `(connection_id, generation)` 已 `closed_at IS NOT NULL` → 必须开 **新 generation**，插入新行，不得 `UPDATE` 旧行；
- 若 durable baseline 显示同一未关闭 generation → 按单调 delta 继续；
- first sight 且无未关闭 baseline → 只建立 baseline，accounted = 0，不把 Clash 累计计数当作本代流量。

`meta.schema_version`（或等价）必须 bump 为 `3`。必须提供 **schema 2 → schema 3** 的显式、可测试迁移：保留历史 `connections` / `daily_usage` 行；为既有行分配 `generation`（建议既有行 `generation=1`）；`instance_id` 保持 NULL；为当时仍 open 的连接建立 `poll_baseline`（若无法安全恢复计数器，则按 unknown 处理：baseline only，宁可少计不可爆计）。

【决策 6】`instance_id` / `event_id` 在 0.2.7 schema 3 **预留**（`instance_id` 可空；`event_id` 已加入并 AUTOINCREMENT）。完整 mint `instance_id` 属于 0.2.8。

## 4.4 Delta 事务与 DB/内存关系（D7 / D8）

【覆盖原 SPEC §4.4 中未强制「先提交 DB 再刷新内存」的顺序。】

**【D7】DB 是 accounting 的唯一 commit point；内存 = cache only。**

强制流程：

```text
read DB baseline
→ calculate delta
→ BEGIN
→ write delta/event + update durable baseline
→ COMMIT
→ 然后才刷新内存缓存
```

`COMMIT` 失败：

```text
ROLLBACK
+ 从 DB 重载缓存
```

禁止 DB/内存漂移。禁止在 COMMIT 之前把内存当作已提交事实。禁止「内存先改、DB 稍后」的双写。

推荐同一事务内完成：accounting 事件行（或对当前 generation 行的更新）+ `poll_baseline` 更新。

**【D8】不用巨额 delta 阈值判断 reset。** 确定性条件：

```text
current < previous     → reset / new generation（永不发出负 delta）
unknown active conn    → baseline only（不把当前计数器当成本代流量）
known same generation  → monotonic delta（current - previous）
```

另加基本整数范围 validation（拒绝负数、非整数、溢出到不合理类型）。**不要** 用「delta 太大所以一定是 reset」这种启发式作为正确性条件。

## 4.5 重启行为

### accountd 重启

当 accountd 重启并看到已经活跃的连接：

```text
known connection + durable DB baseline（同 generation，未关闭）
→ 继续 delta accounting

unknown active connection（无未关闭 baseline）
→ 只建立 baseline
→ 只计此后观测到的 delta
```

**Phase 1a 必须先用单测钉死「重启清零」bug：** 在 schema 3 落地前后，用夹具证明：已记账字节不会因进程重启而被清零、重计或覆盖 closed 行。优先有界少计，而不是灾难性多计。

### sing-box 重启

sing-box 重启后：

- 旧连接状态不得与新计数器合并；
- counter reset 不得产生负 delta 或被当成巨额流量（D8：`current < previous` → 新 generation）；
- baseline generation 必须前进；
- 系统必须内部一致；
- 已 closed 的 generation 仍不得被覆盖。

## 4.6 90 天 raw 审计保留 + 分批 DELETE

默认：

```text
accounting_raw_retention_days = 90
```

【决策 2 / D2】正式冻结 raw = 90。

原始连接/审计元数据必须在配置窗口内可查询。

删除必须：

- 事务大小有界；
- 避免长时间阻塞正常 ingest；
- 不破坏 daily 聚合；
- 不静默删除新于 cutoff 的记录；
- **不被 Fleet cursor 阻塞**（D9）：服务器 retention 是独立规则，**超过 90 天就删**。controller 太久未同步不得要求节点「为了 cursor 而留着」。

**【修正 B】** retention `DELETE` 必须分批：每事务 **≤ 1000–5000 行**（具体常量由 Agent 选定并写入代码/测试，例如 2000），跨多个 maintenance cycle 完成，避免长事务锁。禁止单事务删除整个超窗集合（若该集合可能很大）。

`event_id` 删除后不得被 AUTOINCREMENT 复用（D9）。因此 cursor 过期是预期情况，见 §6 / 0.2.9 的 `CURSOR_EXPIRED`（0.2.7 只需保证 retention 不迁就 cursor；cursor 协议在 0.2.9 实现）。

## 4.7 Daily 聚合（冻结 90 / 90）


这是默认策略，不是计费保证。

现有 UTC 时间语义应保持不变，除非另行批准的迁移改变它们。

未来若产品想要 raw 90 / daily 730，必须 **独立实现** incremental immutable daily rollup；**现在不做**。当前 daily 由 raw 重建，有效窗口本来就无法超过 raw。

**【决策 15 / D18】legacy daily=730 迁移规则（v0.2.7 必须落地）：**

```text
若 source version <= 0.2.6
且 当前 daily_retention = 730（已知旧默认值）
→ migrate 到 90
→ 打日志：
  'Migrated legacy default daily retention 730 → 90.'

其它值（365 / 180 / 30 / 自定义…）
→ 视为管理员显式设置
→ preserve
```

不得把任意非 90 的 daily 值一律改成 90。未来可增加 `retention_policy_origin` 字段；0.2.7 不强制，但迁移规则必须可测试。

## 4.8 Audit 查询：0.2.7 **真正实现**（不是 preserve）

【覆盖原 SPEC §4.8「preserve or add」。】【决策 8 / D11】当前树 **没有** `vcl audit`。v0.2.7 必须新增：

```bash
vcl audit user alice --from RFC3339 --to RFC3339
```

时间参数必须是 RFC3339（例如 `2026-08-10T09:00:00Z`）。

**窗口语义 = 区间相交（interval-overlap），不是「started_at 落在窗内」：**

```text
started_at < query_to
AND COALESCE(closed_at, last_seen_at) >= query_from
```

`vcl stats` 保持 **日粒度**，不与 audit 的连接级窗口语义混用（D11）。

Audit 必须支持按以下维度查询/过滤（至少）：

```text
user
time range（RFC3339，interval-overlap）
destination host/IP
node/instance（instance 在 0.2.7 可为空）
traffic amount
```

## 4.9 Health / verify / accounting check（同一套逻辑）

【覆盖原 SPEC §4.9 把 `vcl accounting check` 写成可能独立的第二套检查。】【决策 3 / D3】

`vcl verify` **就是** 节点健康验证，覆盖三平面：

```text
Proxy Plane
Accounting Plane
Registry / State
```

**Accounting Plane 扩展（0.2.7 必须纳入同一 checker）：**

```text
accountd service 可判定（active / readable）
database readable
schema expected（schema 3）
heartbeat / last successful sample
baseline sanity（durable poll_baseline 与 open connections 一致，无漂移）
counter sanity（无负计数、无不可能总量）
retention state（worker/cutoff 正常，无异常积压）
```

`vcl accounting check` 作为调用 **同一 checker** 的 alias（可提供；**不形成第二套验证逻辑**）。`vcl accounting status` 可保留为运维只读摘要，但不得分叉出另一套判定规则。

未来 `repair` 命令仅可对明确安全的操作添加。没有确认，不得自动破坏性修复。

## 4.10 JSONL ingest：二选一，0.2.7 必须落实（修正 A）

【新增为 SPEC 要求。】当前 `vincula-accountd` 在 `/var/lib/vincula/events.jsonl` 存在且非空时优先 JSONL；offset 仅在内存 `_jsonl_offset`，重启从 0 再读，会重放。

**禁止** 保持「重启会重放」。Agent 必须二选一（在完成报告中写明选择），不得第三条路：

**选项 A1 — JSONL 是 production backend：**

```text
持久化 file identity（inode/dev/size/mtime 或等价，足以检测轮转/替换）
+ 持久化 offset
+ 事件级 dedupe（不得因重启/轮转重复记账）
重启后从 durable cursor 继续，而不是从文件头重放
```

**选项 A2 — JSONL 已无生产用途：**

```text
删除 ingest path（代码、文档、install.manifest、测试夹具中的生产路径）
Clash poll 为唯一生产 collector
测试不得再把 JSONL 当作默认成功路径
```

当前树的 **in-tree 生产 collector 是 Clash poll**；JSONL 依赖树外 producer。两种选项都合法，但必须完整落实所选合同。

## 4.11 Soak 测试与发布门槛

【覆盖原 SPEC §4.10「24h recommended / 72h preferred」与 §11 未把 soak 绑到 READY FOR RC 的表述。】【决策 12 / D20】

注入（单测/集成 + live）：

```text

sing-box restart
reboot
temporary Clash API failure
temporary DNS/network failure
```

验证：

```text
no exploding totals
no negative values
no repeated historical traffic
collector recovers
audit remains queryable
```

**Soak 证据规则（LIVE-ONLY）：**

```text
无 live 24h soak
  → 最高只能报 READY WITH DOCUMENTED LIMITATIONS
     （不得报 READY FOR RC）

24h soak PASS
  → READY FOR RC 的门槛（在其它 P0/P1/迁移证据也满足时）

72h soak
  → recommended evidence，非强制
```

24h soak **必须在真实运行的节点上做**（LIVE-ONLY），不能用加速时钟或纯单测替代该门槛。单测仍必须覆盖重启/复位/事务失败。

## 4.12 v0.2.7 验收标准

- **AC-2.7-01:** accountd 在活跃流量期间重启，不重复已记账字节。
- **AC-2.7-02:** 重启后未知活跃连接建立安全 baseline，而不是把全部历史计数器当流量。

- **AC-2.7-09:** **live 24h soak** 显示没有因重复处理导致的累积 accounting 漂移。无 24h soak 不得报 `READY FOR RC`。
- **AC-2.7-10:** v0.2.6 → v0.2.7 迁移保留用户、凭据、**现有 UUID node_id**、accounting 历史；`is_supported_upgrade_from` 包含 0.2.6。

## 5.8 Host key 安全（D14）

【覆盖原 SPEC §5.8 仅写「不要默认 StrictHostKeyChecking=no」、未钉死 known_hosts / 禁止 /dev/null 的程度。】

**冻结策略：**

- **默认** 使用 OpenSSH `known_hosts`（用户/系统 OpenSSH 文件，controller 不得改用空文件）。
- 首次连接：
  - **交互确认**，或
  - 显式 `--host-key SHA256:...`

- **绝对禁止：**
  - `StrictHostKeyChecking=no`
  - `UserKnownHostsFile=/dev/null`
- 不得全局关闭 host-key checking。
- 节点有意改 IP 时，host key 更新必须显式。

```text
PLANNED → APPLYING → SUCCESS | PARTIAL
```

`PARTIAL` **必须** 列出：

```text
每节点状态：SUCCESS | FAILED
补救命令（管理员可复制执行）
```

best-effort rollback **允许**，但 **不是** correctness guarantee。不得在文档或 CLI 中承诺「跨节点失败会自动完全回滚」。

永远不要在部分 fleet 变更之后报告全面成功。

## 6.8 Fleet audit

示例：

```bash
vcl fleet audit user alice \
  --from "2026-08-14T12:00:00Z" \
  --to   "2026-08-14T18:00:00Z"
```

窗口语义与节点 `vcl audit` 相同：RFC3339 + interval-overlap。

输出应包括：

```text
time
node
instance
destination
traffic
```

审计层必须按稳定 `user_id` 合并记录。

## 6.9 Fleet stats

示例：

```bash
vcl fleet stats user alice --days 7
vcl fleet stats top users --days 30
vcl fleet stats top hosts --days 7
vcl fleet stats node lax --days 30
```

Fleet 总计必须来自带节点标签的记录。

永远不要合并缺乏足够节点身份的记录。stats 保持日粒度，不与连接级 audit 窗口混用。

## 6.10 节点退役

引入生命周期语义：

```bash
vcl fleet node retire lax
```

推荐过程：

```text
verify node identity
→ final fleet sync
→ final audit/accounting snapshot
→ mark instance retired
→ disable/revoke node credentials
→ optional uninstall
→ mark logical node retired or awaiting replacement
```

不要自动擦除历史数据。

## 6.11 Incremental sync 与 cursor（从 0.2.8 移入）

稳定 cursor 机制：

```text
last_event_id
```

远程：

```bash
vcl audit export --after EVENT_ID --jsonl
```

Controller：

```text
只请求新记录
→ 校验 node_id / instance_id
→ import
→ 原子更新 cursor
```

重跑 sync 必须幂等。

**【D9】retention 与 cursor：**

- 节点 90 天 retention **不被** Fleet cursor 阻塞（>90d 就删，0.2.7 已如此）。
- controller 太久未同步 → 显式：

```text
CURSOR_EXPIRED
earliest_available_event_id
snapshot / reseed 路径
```

不得静默空洞同步，也不得要求节点为过期 cursor 保留数据。

## 6.12 v0.2.9 验收标准

- **AC-2.9-01:** 同一用户可开通到两个节点，一个 `user_id`、不同 UUID。
- **AC-2.9-02:** 旋转一个节点的凭据不影响另一节点凭据。
- **AC-2.9-03:** 在一个节点 disable Alice 不会在每个节点 disable Alice，除非显式请求。
- **AC-2.9-04:** Fleet audit 按稳定 `user_id` 合并 Alice 在各节点的活动。
- **AC-2.9-05:** Fleet stats 保留节点归属。
- **AC-2.9-06:** 批量多节点开通检测部分失败，进入 `PARTIAL`，列出每节点状态与补救命令；不承诺分布式 rollback。
- **AC-2.9-07:** credential CSV 包含正确的节点特定链接。
- **AC-2.9-08:** 节点退役在退役状态提交前执行 final sync。
- **AC-2.9-09:** 节点退役后历史审计仍可查询。
- **AC-2.9-10:** 不引入管理 API 端口。
- **AC-2.9-11:** 节点端 `vcl user add --user-id` 可用；普通 add 仍由节点生成 `user_id`；controller 注入全局 `user_id`。
- **AC-2.9-12:** `vcl audit export --after event_id` + incremental sync 幂等；过期 cursor 返回 `CURSOR_EXPIRED` + `earliest_available_event_id` + reseed 路径。

# 7. v0.3.0 — Backup / Replace / Restore

## 7.1 目标

让 VPS 基础设施可丢弃，同时保留身份与审计连续性。

主要用例：

```text
VPS IP 变更
VPS 供应商变更
VPS 即将退役
VPS 丢失
新 VPS 替换旧 VPS
管理员需要灾难恢复
```

## 7.2 备份类别

### A. Identity/Audit Backup — 默认（secretless）

【决策 14 / D17】默认备份 = **secretless**，**无加密要求**。

默认备份应保留：

```text
logical node_id
instance history
user_id
user metadata
credential history metadata
accounting history
audit history
policy/configuration metadata
```

不应要求保留有效密钥。这是首选的迁移/替换备份。

实现：使用 **Python SQLite Backup API**（或等价一致快照），不要对 live SQLite 做无证明安全性的朴素文件拷贝。

### B. Full Disaster-Recovery Backup — 显式，age 加密

可选：

```bash
vcl backup create --include-secrets
```

可能包含：

```text
Reality private key
active UUID credentials
Clash API secret
其它有效密钥状态
```

含密钥的备份 **不得** 以未加密的普通归档发出。

**【D17】加密冻结为 age：**

```text
--include-secrets → age 加密 mandatory
无 age → ERROR：
  'Secret-bearing backup requires age.'
age 为可选依赖（secretless 默认备份不需要 age）
```

【覆盖原 SPEC §7.2「Encryption is mandatory」未指定算法。】不得用未指定的 zip 密码或其它临时方案替代 age。

## 7.3 拟定 CLI

最低限度：

```bash
vcl backup create
vcl backup create --include-secrets

vcl backup verify FILE

vcl restore FILE
vcl restore FILE --replace-node NODE

vcl fleet node replace NODE --host NEW_HOST
```

具体语法可以演化，但语义必须明确。

## 7.4 备份清单

每个备份必须包含至少含有以下内容的 manifest：

```text
backup schema version
Vincula version
created_at
source node_id
source instance_id
included components
secret-bearing flag
encryption = none | age
hashes/checksums
```

必须在 restore 变更之前做备份校验。

## 7.5 安全替换默认

节点替换时，默认行为应为：

```text
preserve:
  node_id          （现有 UUID，不重铸）
  user_id
  user metadata
  accounting history
  audit history

replace:
  instance_id      （新 UUID，禁止复制 node_id）
  endpoint/IP
  Reality keys
  Clash secret
  active credential UUIDs
```

然后生成新的客户端链接。

## 7.6 凭据重发

替换后：

```text
旧节点凭据 → revoked/retired
新节点凭据 → active
```

系统应生成 reissue 报告：

```csv
user,node,old_credential_id,new_credential_id,vless_uri
...
```

## 7.7 旧 VPS 可能失信的假设

替换工作流应假设旧 VPS 可能不再可信。

因此：

- 默认不复用旧 Reality 私钥；
- 默认不复用旧 Clash secret；
- 默认不复用有效 UUID；
- 保留身份与历史，而不是密钥。

## 7.8 仅 IP 变更、不替换 VPS

只改公网 endpoint 可以使用更轻的操作。

示例：

```bash
vcl fleet node set lax --host 203.0.113.28
```

若同一实例仍有效，管理员可以保留凭据。

系统必须区分：

```text
endpoint rebind
```

与：

```text
physical instance replacement
```

Host key 更新仍必须显式（D14）。

## 7.9 Restore 信任检查

Restore 之前：

```text
verify archive hash
verify backup manifest
verify schema support
verify target node state
verify node_id semantics
verify secret mode（secretless vs age）
verify age 可用性（若 secret-bearing）
```

不得自动覆盖无关的已有 Vincula 安装。

## 7.10 Accounting 数据库快照

备份必须使用一致的 SQLite backup/snapshot 方法（Python `sqlite3.Connection.backup` 或文档化的等价物）。

不要用朴素文件拷贝复制 live SQLite DB，除非实现证明对所选 journal mode 是安全的。

## 7.11 Restore 事务

推荐：

```text
validate backup
→ inspect target
→ generate replacement plan
→ create target-side safety backup
→ stage restored canonical state
→ generate new secrets if safe mode
→ generate config
→ validate
→ start proxy/accounting
→ health checks
→ commit
→ emit credential reissue CSV
```

失败必须保留可恢复的目标状态。这是 **单节点** INV-05 事务，不是跨节点分布式事务。

## 7.12 实例历史

保持足够元数据以回答：

```text
在给定历史时期内，哪个物理 VPS 实例服务了逻辑节点 lax？
```

建议概念模型：

```text
node_id
instance_id
started_at
retired_at
endpoint metadata
status
```

`instance_id IS NULL` 的历史 accounting 行仍表示「当时未跟踪物理实例身份」。

## 7.13 v0.3.0 验收标准

- **AC-3.0-01:** 默认备份包含替换所需的身份/审计/accounting 状态。
- **AC-3.0-02:** 默认备份不要求复用有效密钥（secretless，无加密要求）。
- **AC-3.0-03:** 含密钥备份用 **age** 加密；无 age 时 ERROR `'Secret-bearing backup requires age.'`。
- **AC-3.0-04:** 备份校验能检测损坏。
- **AC-3.0-05:** 替换 VPS 保留 `node_id`。
- **AC-3.0-06:** 替换 VPS 生成新的 `instance_id`（不复制 `node_id`）。
- **AC-3.0-07:** 安全替换默认旋转 Reality 与用户凭据。
- **AC-3.0-08:** 用户 `user_id` 保持不变。
- **AC-3.0-09:** 替换后历史 accounting/audit 仍可查询。
- **AC-3.0-10:** 新凭据 CSV 正确生成。
- **AC-3.0-11:** 撤销完成后，旧凭据链接失败。
- **AC-3.0-12:** restore 失败不会静默摧毁目标或源状态。

# 9. 版本与 Version Bump 标准

## 9.1 Vincula pre-1.0 版本策略

Vincula 处于 1.0 之前，使用务实的项目版本策略。

格式：

```text
MAJOR.MINOR.MILESTONE
```

当前路线图示例：

```text
0.2.7
0.2.8
0.2.9
0.3.0
0.3.1
```

该策略有意比临时改版本更严，但不要求在 1.0 之前完全等同公开库 SemVer。

## 9.2 MAJOR bump

```text
0.x.y → 1.0.0
```

仅当 Vincula 具备适合长期支持发行的稳定产品合同时。不属于本 SPEC。

## 9.3 MINOR bump

示例：

```text
0.2.x → 0.3.0
```

当发生以下一项或多项时必须：

```text
持久身份模型发生实质性变化
引入新的信任边界
引入 backup/restore 合同
磁盘状态架构发生实质性变化
有意引入破坏性 CLI 行为
兼容合同显著变化
```

对本路线图，v0.3.0 成立是因为它引入：

```text
backup format
restore semantics
node replacement semantics
instance history
secret rotation/reissue workflow
age 加密合同
```

## 9.4 MILESTONE bump

示例：

```text
0.2.6 → 0.2.7
0.2.7 → 0.2.8
0.2.8 → 0.2.9
0.3.0 → 0.3.1
```

用于同一架构世代内向后兼容的产品里程碑。

示例：

```text
Stability & Audit Foundation
Fleet Foundation
Fleet Users & Audit
Local Audit UI
```

里程碑可以包含附加 schema 迁移，若兼容与迁移被显式支持。

**【D1】** 当前树必须立即使用 `0.2.7-dev`，不得继续用 `0.2.6` 标签发布已分叉的代码。

## 9.5 运行时产品版本 vs schema 版本

不要把 `VINCULA_VERSION` 当作唯一的 schema 迁移键。

每种持久格式在适当时必须有自己的 schema 版本。

示例：

```text
state.json.schema_version
users.json.schema_version
accounting.db PRAGMA/user_version 或 schema 表（0.2.7 → 3）
fleet registry schema_version
backup schema_version
```

规则：

```text
产品版本 bump
并不自动要求 schema bump

schema 变更
要求 schema 版本 bump

schema 迁移
必须显式且经过测试
```

v0.2.7 同时 bump 产品版本（0.2.6 → 0.2.7）**和** accounting schema（2 → 3）。这是有意的，不是「产品 bump 自动改 schema」。

## 9.6 包修订号

为避免用计划中的里程碑号去做仅打包或冻结后的修正，Vincula 可以维护单独的 package revision。

示例概念构建 ID：

```text
0.2.7-r1
0.2.7-r2
```

推荐字段：

```text
VINCULA_VERSION=0.2.7
PACKAGE_REVISION=1
```

仅在以下情况使用 package revision：

```text
无持久 schema 变更
无兼容合同变更
无迁移语义变更
无功能里程碑变更
```

示例：

```text
文档修正
release archive 重建
打包元数据修正
非功能性 bootstrap 打包修复
```

若运行时行为、安全语义、持久化或用户可见行为发生实质性变化，应 bump 产品里程碑。

## 9.7 开发与 RC 标识符

开发期间：

```text
0.2.7-dev
```

【D1】Agent 进入本 SPEC 的 **第一件事** 就是把树标成 `0.2.7-dev`。

Release candidate：

```text
0.2.7-rc.1
0.2.7-rc.2
```

冻结发行：

```text
0.2.7
```

等价标识符可以存在构建元数据中，但发行工具必须暴露确切的构建身份。

## 9.8 Version bump 决策表

| 变更 | 所需 bump |
|---|---|
| 仅文档 | package revision 或不做运行时 bump |
| 仅重建 release archive | package revision |
| 发行前小的向后兼容 bug 修复 | 留在当前 `-dev` / `-rc` |
| 发行后小的运行时 bug 修复 | 下一 milestone，除非严格仅打包 |
| 当前架构内新 CLI 功能 | milestone |
| 附加的向后兼容 schema 变更 | milestone + schema bump |
| 破坏性 schema/身份/信任模型 | minor |
| backup/restore 兼容世代变更 | minor 或按影响显式 bump backup schema |
| 公开稳定 1.0 合同 | major |

# 10. 冻结标准

一个版本在以下情况视为冻结：

```text
全部要求的验收标准通过
迁移测试通过
rollback 测试通过
已知 P0 = 0
已知 P1 发行阻断 = 0
文档已更新
release artifacts 可复现
release lock/checksums 已生成
```

对 **v0.2.7**：另见 §11 / D20：无 live 24h soak 则 **不能** 以 `READY FOR RC` 进入 RC，只能 `READY WITH DOCUMENTED LIMITATIONS`（若其它门槛满足）。

冻结后：

```text
无新功能工作
```

仅：

```text
P0
P1 回归
安全修复
发行/打包修正
```

可以修改发行分支。

# 11. 发行门禁标准

每个里程碑必须报告以下之一：

```text
READY FOR RC
READY WITH DOCUMENTED LIMITATIONS
NOT READY FOR RC
```

`READY FOR RC` 要求：

```text
全部 P0 已修
全部发行阻断 P1 已修
迁移证据
rollback 证据
fresh-install 证据
相关的 reboot 证据
无未解决的数据丢失风险
```

**【D20 / 决策 12】对 v0.2.7 额外强制：**

```text
无 live 24h soak     → 不得报 READY FOR RC
                       若其它项满足，最高 READY WITH DOCUMENTED LIMITATIONS

24h soak PASS        → 才允许 READY FOR RC（仍须满足上表）

72h soak             → recommended evidence，非强制
```

【覆盖原 SPEC §11 未把 24h soak 绑到 READY FOR RC。】

有文档的产品限制可以接受，若它们是有意的且不违反该版本声明的合同。

# 12. 跨版本迁移要求

# 14. 安全要求

所有版本：

- 默认无公网管理 API；
- SSH host 验证不得被全局关闭；**禁止** `StrictHostKeyChecking=no` 与 `UserKnownHostsFile=/dev/null`（D14）；
- 生成的凭据导出必须权限收紧；
- 密钥不得写入普通日志；
- 私钥不得出现在 audit 事件中；
- 含密钥备份必须 **age** 加密（D17）；secretless 默认备份不要求加密；
- 第一方发行产物保持完整性校验；
- 破坏性 restore/retire 操作需要显式目标校验；
- 不得静默删除历史 accounting/audit 数据（90 天 retention 是声明的策略，不是静默删除）；
- v0.3.1 UI localhost-only、只读、无公网面板。

# 15. 仓库与打包要求

【覆盖原 SPEC §15「Preferred: src/canonical tree」。】【决策 9 / D12】

Canonical source 必须有且仅有一个权威位置。

**不要** 手工维护两份可编辑副本，例如：

```text
repo root
release/
```

**冻结布局：**

```text
canonical = 仓库根目录
  vincula.sh
  bin/
  lib/
  scripts/
  tests/
  docs/

generated = dist/
  dist/vincula-node-x.y.z.tar.gz      （0.2.8+）
  dist/vincula-controller-x.y.z.zip   （0.2.8+）
  （0.2.7 仍可先发 Linux node tar.gz；controller zip 从 0.2.8 起必达）

release.lock
       ↓
archive + SHA256
```

**【不要搬 `src/`。】** 不要为了「看起来更像标准 Python 包」而重排 canonical 树。

0.2.8+ 两个 artifact 共用 Python domain library / JSON schema / query model；controller 侧无 root/systemd/`/etc/vincula`。

# 20. v0.3.1 时的最终产品边界

在 v0.3.1 结束时，Vincula 应支持如下工作流：

```text
管理员（Windows 11 工作站优先）
    │
    ├── 安装若干 VPS 节点（Linux node artifact）
    ├── 用 CLI 管理用户与凭据（含 --user-id / fleet 注入）
    ├── 把一个用户分配到一个或多个节点
    ├── 审查约 90 天的目的地级审计元数据（CLI + 只读 UI）
    ├── 聚合近似用量（日粒度 stats）
    ├── 经 SSH 管理节点（known_hosts 策略）
    ├── 退役/替换 VPS 实例（PARTIAL 显式；替换 mint 新 instance_id）
    ├── 保留逻辑身份与审计历史（node_id 不重铸）
    ├── 在安全替换期间旋转密钥（secretless 备份；secret 备份用 age）
    └── 使用 localhost-only 只读 UI 做便利查阅
```

没有：

```text
公网管理 API
公网 Web UI / Web 管理面板
计费引擎
支付系统
自助门户
MITM 内容检查
机场式控制面板
第一版 UI mutation
分布式自动 rollback 承诺
```

期望的最终性质：

> VPS 实例是可丢弃的执行基础设施。用户身份、逻辑节点身份、审计历史、accounting 历史，以及管理员控制的 fleet 状态，才是耐久系统。
